# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Rackoon is an agentless SSH server manager for self-hosters (Docker Compose + Tailscale). Mac app first (SwiftUI), then iPhone, then Android. Product scope, MVP requirements (M1–M12) and phase gates are in [docs/PRD.md](docs/PRD.md). Only the MVP is scoped in detail. Work proceeds in approved stages (Stages 0 to 3 done: bootstrap, SSH transport + terminal spike, Overview/attention, saved servers + host-key trust, terminal tabs, Docker); do not build ahead of the stage the user has approved.

## Commands

Run from the repo root unless noted. In interactive zsh, don't paste commands with trailing `# comments` (they become arguments).

```

cd apple && swift build --product RackoonMac

tools/install-app [--dev] [version]       # make-app, then copy into /Applications (quit the running copy first)

cd apple && swift test                    # needs full Xcode with its licence accepted (XCTest)
cd apple && swift test --filter ModelsTests/testServerRoundTripsThroughJSON   # single test
cd apple && swift test --filter RackoonMacTests  # the Mac app's own tests (icon store files and uploads, NAS model; AppKit, no network)
```

```

cd apple && swift run rackoon-probe <host> updates     # apt pending/security/held counts (read-only, from apt's local cache)

cd apple && swift run rackoon-probe <host> file-test     # REAL read/validate/save of compose and .env on a throwaway stack under /tmp (creates and removes it)
```

No linter or formatter is configured yet (`swift-format` is not installed). CI is `.github/workflows/ci.yml` (check-spec on Linux; `swift test`, build and `tools/make-app` on `macos-26`, because SwiftTerm 1.99 needs Swift 6.2+ and on an older runner SwiftPM silently fell back to SwiftTerm 1.20.0). Every push uploads `Rackoon-<version>-macos-arm64.zip` plus a `.sha256` as the `Rackoon-macOS-arm64` workflow artifact (14 days); pushing a `mac-v*` tag (e.g. `mac-v0.1.0-alpha.2`) also publishes them as the GitHub Release "Rackoon for Mac <version>" (a version with a suffix is a pre-release; Apple silicon, ad-hoc signed, not notarized, so first launch needs right-click Open). Each platform has its own tag prefix and release (`mac-v*`, `android-v*`) so a release page is about one platform; the first release, `v0.1.0-alpha.1`, predates this and is the Mac one. Notarizing needs a Developer ID certificate and secrets, which are not set up.

Xcode is installed on the dev machine. There is no `.xcodeproj` yet. The Mac app is a SwiftPM executable target, which needs the `AppDelegate` activation-policy workaround in `RackoonApp.swift` to show a window under `swift run`. A real Xcode project is needed before signing and notarizing.

## Architecture

**Two native cores kept in parity by a shared spec.** The server logic (shell commands, text parsers, attention rules) is small. It is implemented twice: Swift in `apple/` and, in Phase 4, Kotlin in `android/`. `spec/` is the language-neutral source of truth, so edit `spec/` first and make platform code follow:
- `spec/commands.json`: every shell command we run on a server (id, script, timeout, distros).
- `spec/models.schema.json`, `spec/attention-rules.json`: model shapes and the needs-attention rules.
- The Swift command string (`ServerSession.overviewCommand`) must equal the `script` in `commands.json`; a test enforces it. Edit both together.
- `spec/fixtures/<command-id>/NAME.out.txt` + `NAME.expected.json`: captured real output and the expected parse. Every platform's parsers must match these golden files. `tools/check-spec` fails if a command has no fixtures or a fixture has no expected output.

**Layering (same on every platform):** UI → view model/state → services → `SSHTransport` → SSH implementation.
- `RackoonCore` (`apple/Packages/RackoonCore`) is Foundation-only and must never import SwiftUI, AppKit or `Process`. It defines the `SSHTransport` protocol (`run`, `stream`) that every transport implements. Services take a transport by injection, so tests use a fake that replays fixtures.
- `RackoonSSHSystem` is macOS-only. `OpenSSHTransport` wraps `/usr/bin/ssh` (ControlMaster, BatchMode) so `~/.ssh/config` and ssh-agent work. An embedded-SSH transport (App Store, iOS, Android) swaps in later without touching Core.
- `RackoonMac` (`apple/Apps/RackoonMac`) is the thin SwiftUI app. It depends on both packages.
- The single `apple/Package.swift` uses custom `path:` entries into `Packages/*/Sources/*`, so the layout is not the SwiftPM default.

**Design constraints to keep Android and the App Store possible:**
- No Mac-only assumptions in Core. `~/.ssh/config` parsing is a Mac-app feature that produces plain `Server` models.
- Parsers stay simple (line/column splitting, or JSON from `docker ps --format json`) so they port 1:1 to Kotlin.
- `ServerSession` (Core actor) owns one server's transport, the 5 s poll loop and the last good `ServerState`. A failed poll keeps the old data and sets `error`. CPU % needs two readings, so `Overview` carries raw `/proc/stat` counters and `cpuPercent(since:)` does the delta. `ServerModel` (Mac app) bridges the actor to SwiftUI; views never call SSH directly. `Attention.evaluate` is a pure function of an `Overview`.
- Persistence: `ServerStore` (Core) writes `servers.json` and per-server cached snapshots under `~/Library/Application Support/Rackoon/`. Secrets never go there. The app was called Homebase until it became Rackoon: `ServerStore.defaultStore()` copies a legacy `Homebase/` folder once, and `RackoonApp` copies the old `HomebaseMac` defaults keys once; both leave the old data in place. On select, `AppModel` paints the cached snapshot immediately (`ServerState.isStale`) and replaces it on the first successful poll.
- Host keys: `HostKeyVerifier` (SSHSystem) runs ssh with `StrictHostKeyChecking=yes`. Unknown key -> user sees fingerprints and confirms -> exactly the scanned lines are appended to known_hosts. Changed key -> blocked, never offered for acceptance. `AppModel` polls the selected server every 5 s; `FleetMonitor` (owned by `AppModel` as `fleet`) polls every other saved server once a minute (`ServerSession` with a 60 s interval, over the same ControlMaster) for its sidebar status light and tooltip. It checks each host key once per run before polling (skipped when `AppModel` already found it trusted); an unknown key shows grey and is never polled, a changed one red. The server being left is handed over with its fresh reading (`seed`), Edit Connection and removal `reset` it, wake from sleep refreshes all. Background polls save snapshots like the selected one does.
- `Server.host` is whatever ssh connects to (hostname, IP or ~/.ssh/config alias). Imported servers keep the alias as `host` so ssh applies the rest of the entry.
- Server menu (`ServerSwitcher.swift`): the sidebar shows only the selected server as a card (light, name, `user@host[:port]`, like the Appearance card) with a count or "N down" beside the Servers heading. Clicking it (or Go > Switch Server… ⌘K) opens `ServerSwitcherPanel`, drawn as an overlay over the whole window (`ServerSwitcherState`, coordinate space `rackoon.window`) so a click anywhere closes it. Like a macOS pop-up button the selected row opens over the card, reaching up and down, pushed back inside the window and clear of the traffic lights (`ServerMenuLayout` in Core, tested); the search field and + (Add server) sit in its footer and the list keeps its height while filtering (`ServerList.filter`: every word in name/host/user/alias). Drag a row to reorder (live, `ServerList.moving(_:onto:)`; disabled while searching) or right-click > Move Up/Down, Edit Connection…, Remove. `AppModel.reorder` saves the order to servers.json, which the Go menu follows.
- Dashboard (`DashboardScreen.swift`, `Screen.dashboard`, the sidebar's top row and Go > Dashboard ⌘0; not one of a server's screens, `Screen.serverScreens` excludes it): a horizontal paging carousel (`scrollTargetBehavior(.paging)`, page remembered in `@AppStorage("dashboardPage")`, also launchable with `-dashboardPage docker`) of six pages (Services and Alerts are described under their own entries below) built from `AppModel.fleetRows` (selected server's live state + `FleetMonitor`'s once-a-minute states + `HealthHistory`). Health: fleet totals (`FleetTotals`, CPU weighted by cores) and per server an Uptime-Kuma-style heartbeat bar and uptime % plus Beszel-style CPU/memory sparklines (Swift Charts, fixed 0–100 scale, hover readout) and fullest disk. History is `HealthHistory` (Core, tested): one sample a minute, every up/down change kept, last 60, in memory only (`FleetMonitor.record`, fed by both polls). Servers: a tile per server (host, OS, IP/Tailscale IP, CPU/RAM/disk meters with values, uptime, update/reboot/unhealthy badges), click = its Overview. Docker: fleet container totals, then per server its `DockerTotals` (container CPU as share of host, memory, the disk holding /var/lib/docker found from the Overview's mounts) and a tile per stack (services, images, usage, `DockerStack.mainWebPort` as a link to http://<tailscale or LAN IP>:<port>), click = that stack's page. Bookmarks: per server, Homepage groups as columns. The Docker and Bookmarks pages attach every ANSWERING server's `DockerModel` while visible (`DockerAttachment`), never an unanswering or untrusted one.
- Terminals: `TerminalStore` holds each server's `TerminalTab`s; a tab owns its SwiftTerm `LocalProcessTerminalView` (not SwiftUI), so sessions survive switching screens, tabs and servers, and end only on tab close, server removal or quit. Tabs run `ssh -t` over the same ControlPath as `OpenSSHTransport`, so a new tab reuses the open connection (about 0.17 s vs 0.8 s). Tabs can be renamed: click the name of the selected tab (or right-click > Rename Tab…) to edit it in place, Return or clicking away saves, Esc cancels, empty restores `TerminalTab.defaultTitle`, names are cut at 40 characters; names live only as long as the tab. Cmd+T / Cmd+W are menu commands (`TerminalCommands`) that replace File > Close and fall back to closing the window when no terminal is showing.
- Docker: `DockerSession` (Core actor, polls every 10 s only while the Docker screen is open, because `docker stats` takes ~2.5 s) parses `docker ps -a` + `docker stats` into stacks grouped by compose project label. A container with no project label (started with `docker run`) is a stack of its own (`isStandalone`, named after the container); `DockerStack.id` is the project name or `standalone/<container>`, and everything that remembers a stack (open page, `busyStacks`, an output's scope, `removing`/`createdStacks`) is keyed by id because a container may share a project's name. Cards show `kindLabel` ("Compose Stack" / "Standalone") where the compose file name used to be. A standalone stack's page has the same Stack Actions menu: Pull Latest Image (`StandaloneAction.pullImage`, spec `docker_pull_image`; only a real image reference, never an image id), Restart/Start Container (the container's `DockerAction`), Delete Container (`.remove`, spec `docker_remove`, `DeleteContainerSheet`: typed name always, optional `-v` for anonymous volumes); Update, Rebuild and Recreate are shown disabled with the reason, because nothing holds a `docker run` container's definition to recreate it from. The Android core still groups standalone containers into one "Standalone" stack. Actions (`start/stop/restart`) and logs only accept a hex container id (`DockerSession.isContainerID`), since the id is interpolated into a remote shell command. The Overview command also lists unhealthy container names, which feed the attention strip; each chip links to its `fix` screen.
- Streams (`OpenSSHTransport.stream`, used for logs) deliberately use their own connection with `-tt`, not the shared ControlMaster: stopping a stream sends Ctrl-C through the pty, and tested behaviour is that Ctrl-C reaches the remote command on its own connection but not through a multiplexed one. Merely killing the local ssh leaves `docker logs -f` running forever on Tailscale SSH servers.
- Process plumbing: every child process (ssh, tar, ssh-keyscan/keygen) runs through Apple's `swift-subprocess` (the one dependency of `RackoonSSHSystem`; Core stays dependency-free), not hand-rolled `Process`/`Pipe` code. Commands (`run`) use `Subprocess.run` with bytes output and a task-group timeout (the loser is cancelled and swift-subprocess kills the child). Streams (`stream`) use `.inputWriter` + `.sequence` + `.combinedWithOutput`; cancelling a stream first types Ctrl-C into ssh's stdin writer (`StdinBox`), then cancels the task, whose teardown sequence is a two-second no-op signal (a grace period) before swift-subprocess's final kill. Transfers (`OpenSSHTransfers.swift`) feed ssh's stdin from the file or from a staged tar, and pipe ssh's stdout into `tar -x` for folders; a cancelled task kills every child. A child's exit code is `OpenSSHTransport.exitCode(_:)` (the signal number if it was killed). The terminal tabs are different: SwiftTerm's `LocalProcessTerminalView` owns that process. Proven against the real server by the `files-test`, `compose-test`, `apt-stream-check`, `logs` and `hostkey` probes.
- Fixtures from real servers must be sanitized before committing (IPs, private container names, emails). `spec/fixtures/**/raw-*` is git-ignored for raw captures. Golden files may be generated with `RACKOON_WRITE_GOLDEN=1 swift test`; review them by hand.
- Themes drive the whole app. `apple/Apps/RackoonMac/Resources/themes.json` (hex strings; loaded via `Bundle.module`; validated by `ThemeCatalog` in Core and `tools/check-spec`) holds 45 themes: Rackoon Dark/Light are ours, 43 come from the open iTerm2-Color-Schemes collection (MIT) via `tools/import-themes` (deterministic, fetches only raw.githubusercontent.com, writes `Resources/SOURCES.md`). Do not script-download from terminalcolors.com: its `robots.txt` disallows `/downloads/`. `AppearanceStore.shared` (`@MainActor @Observable`) holds the selection (`"automatic"` by default = Rackoon Dark/Light following macOS via KVO on `NSApp.effectiveAppearance`, which only reflects the system while `NSApp.appearance` is nil, so `recompute()` sets/clears the override first and reads the system value second; or a theme id), the resolved theme, and the `AppPalette` derived from it (`AppPalette.derive` in Core: surfaces are stepped from the theme background; text/accent/status colours are clamped to minimum WCAG contrast; a test runs over every bundled theme). `Theme.*` tokens are computed from that palette, so views update only if they read tokens inside `body` (do not cache colours in `@State` or AppKit views). The root view sets `.tint`, `.preferredColorScheme` and `NSApp.appearance` so system controls and sheets match. Terminals are recoloured via `TerminalStore.applyTheme` (`onChange(of: resolvedTheme)`). The picker is the Appearance row at the bottom of the sidebar (`AppearancePicker` popover), which also holds the Highlight output switch.
- Terminal output highlighting: SwiftTerm's `LocalProcessTerminalView` feeds pty output to the terminal internally (private adapter, no hook, and `inputSender.replaceDelivery` is internal), so output cannot be intercepted in-process without replacing the view. Instead each tab runs `rackoon-pty -- /usr/bin/ssh ...` (`apple/Apps/RackoonPTY`): a pty relay that copies input through untouched, forwards resizes/signals/exit status, and passes ssh's output through `TerminalOutputFilter` (Core, pure, heavily tested), which wraps IPs, error/warning/success words and high percentages in SGR colour pairs from the active theme's palette. The filter never touches escape sequences, the alternate screen (vim/htop), or text a program has already coloured, and skips matches that touch a chunk edge. The relay is located next to the app executable (built as a dependency of RackoonMac); if missing, tabs run ssh directly. Tabs always start through the relay (with `--no-highlight` if the setting is off), and the Highlight output switch takes effect immediately on open tabs: the app sends SIGUSR1 (on) / SIGUSR2 (off) to the tab's `shellPid`, which is the relay. The relay installs its signal handlers before forking, then publishes `/tmp/rk-<uid>/relay-<pid>.ready` (removed on exit); `TerminalTab.setHighlight` only signals a relay whose marker exists (those signals terminate a process without handlers) and retries for a few seconds while it starts, guarded by a per-launch generation so a stale task cannot signal a newer relay. Signal handlers also poke a self-pipe so `poll` wakes immediately. The setting reaches tabs through `onChange(of: appearance.highlightOutput)` in `ContentView`, not a global callback (a `@State` default like `TerminalStore()` is constructed on every parent re-evaluation and all but the first instance are discarded, so constructors must have no side effects). The filter tracks escape state even while off, so switching on mid-vim is correct. Run `tools/test-pty-relay` after touching the relay or filter.
- Updates: `UpdatesSession` (Core) runs the read-only `updates` command (`apt list --upgradable`, held packages, cache age, reboot flag) and `UpdatesParser` turns it into an `UpdatesSnapshot`; a package is security if any of its suites ends in `-security`. The Overview command also carries a `##security` count so the attention strip can show `security_updates` without opening the Updates screen. The Updates screen is `UpdatesScreen` + `UpdatesModel` (reads on open and after each action, no polling; Refresh Lists / Install All / Install Security Updates go through the confirm sheet). The Overview command also carries `##updates` (total) and `##security` counts from one `apt list` call; they drive the dot on the sidebar's Updates row (`UpdateBadge`, amber if any security). `RACKOON_DEMO_UPDATES=1 swift run RackoonMac` fakes a server with pending updates (canned data, nothing is sent) so the screen and dot can be seen when the real server is up to date.
- Branding: `assets/icon/rackoon-icon.svg` is the source of the icon; `RackoonMac/Resources/rackoon-icon.png` is a 1024 px render (`qlmanage -t -s 1024`). `AppIcon` draws it in the macOS rounded-square shape for the Dock (needed under `swift run`; a real bundle should ship an .icns instead) and `AboutView` (a `Window` scene, opened from the app menu's About item) shows it.
- Compose stack actions (`ComposeAction` pull / up / rebuild (`up -d --build`) / recreate, in `DockerSession.swift`) run `cd <dir> && docker compose -p <project> -f <file> [-f <file>...] ...` from the stack's own labels (every file of the comma-separated `config_files` label, in order; `DockerContainer.configFiles`). If a project's containers disagree on directory/files, the stack gets none and the command is nil. The project name must match `^[a-z0-9][a-z0-9_-]*$`, paths must be absolute and are single-quoted with `ShellQuote` (tested through a real `/bin/sh`), and anything unsafe or missing makes the command nil, so nothing is sent. They are `.mutate` intents. The probe's docker mode checks every stack resolves with a harmless `config -q`; it never pulls or recreates. `DockerState.busyStacks` marks a stack busy by project name for the whole action (container ids change when `up -d` recreates). The UI is the ⋯ menu on each stack header (`StackCard.stackMenu` -> `DockerModel.request(_:on:)`, with `composeBlockedReason` explaining why it is disabled); Recreate is marked destructive in the confirm sheet.
- Apt actions (`AptAction` in `AptActions.swift`: refresh, upgradeAll, upgrade(packages:)) run through `UpdatesSession.perform`, which then re-reads the update list. The shell prefix uses root directly or `sudo -n` (never prompts), `DEBIAN_FRONTEND=noninteractive LC_ALL=C`, `--force-confold`, and never `dist-upgrade`/remove/autoremove. Package names are validated against Debian naming, de-duplicated and capped at 200 (`AptAction.maxPackages`; callers fall back to upgradeAll) before being joined into the command; failures are explained from stdout and stderr together (sudo's localised messages are recognised by their `sudo:` prefix). sudo/lock failures get readable messages. Unit-tested (including a real `/bin/sh` run with stub `apt-get`/`sudo`), deliberately never run against a real server. No UI yet.
- App bundle: `tools/make-app` assembles `build/Rackoon.app` (executable `RackoonMac`, the relay next to it in Contents/MacOS, SwiftPM's resource bundle in Contents/Resources, `AppIcon.icns` from `tools/make-icns.swift`, Info.plist with the version). Load bundled files through `AppResources`, never `Bundle.module` directly: its generated accessor looks beside the .app (code signing rejects unsealed files there) and traps if the bundle is missing, which crashed the first bundled build. A bundle id changes the UserDefaults domain, so `RackoonApp` copies keys from the earlier `RackoonMac`/`HomebaseMac` domains once. The Docker screen (`DockerScreen.swift`) is a grid of `StackTile` cards; the overview has a search field (stack, folder, container, service, image; `DockerStack.matches`) and status chips (`DockerStack.Health`: running / needs attention / stopped). Clicking a card opens `StackDetail` (breadcrumb; ONE "Stack Actions" menu holding Update, Pull Latest Images, Rebuild, Restart All, Recreate, Delete, each with a one-line explanation, so nothing that changes the server is one click away; a container list whose rows select which logs to show, with a Shell button and an ⋯ menu (also the right-click menu: logs, shell, copy name, Restart…/Stop…/Start, Rebuild from Dockerfile…), never inline action links next to the row's click target; and a framed right panel whose Logs tab is the live log view; the compose.yaml and .env tabs are placeholders for the editor stage). Shell opens a terminal tab running `DockerSession.shellCommand` (`docker exec -it <id> ...`, spec kind "interactive") via `TerminalStore.newTab(for:title:command:)`. Do not `pkill -x RackoonMac`: it also kills the user's own `swift run` instance; match the exact path.
- Stack files (`StackFiles.swift`, `StackFileCommands.swift`, `StackFileSession.swift`, `LineDiff.swift`; spec `file_read`, `file_validate`, `file_write`): backend for the compose/.env editor. Only a stack's own compose files and `<working_dir>/.env` are editable (`StackFiles.editable`); anything else gives a nil command. Reading is `file_read` (sha256 + base64, 64 KiB cap because content travels inside one remote command argument, base64-encoded and never as text). Checking runs the server's own `docker compose config -q` against a temp copy in the same folder (`-f` list with the edited file swapped for `"$T"`, or `--env-file "$T"` for .env), so relative paths and interpolation resolve exactly as on deploy. Saving (`.mutate`, `FileEdit` + `StackFileSession.confirm/save`) re-checks, refuses if the file's sha256 changed since it was opened (`##changed`), keeps `<file>.rackoon.bak`, preserves owner and mode (`--reference`), then `mv`s atomically. `Intent.preview` carries a readable diff for the confirm sheet because the command itself is not readable. Newer compose reports syntax errors as `at L4.C12:` and names the temp file; `ComposeIssueParser` and `ComposeIssue.naming` normalise that. Command templates are filled in one pass (`Template.fill`), never by sequential replacement. The editor UI: `StackPanel` (tabs: Logs, each compose file, .env) with `FileEditorBody` (code view, checklist, Revert / Save / Save and Redeploy) in `StackPanel.swift`; `StackEditorModel` holds one draft per opened file, checks the exact current text on the server after a 600 ms pause (`validatedText` guards against showing an old result for new text; `.env` syntax is also checked locally with `EnvSyntax`), and only enables Save when that check passed. `EditorChecks.rows` (Core, tested) builds the checklist. Save and Redeploy asks once (diff + the `up -d` command), saves, then runs `DockerModel.runDirect(.up)`. A save refused because the file changed on the server shows Reload from Server / Keep Editing; there is deliberately no overwrite. `CodeEditorView` is an NSTextView wrapper (own ruler with line numbers, bands behind changed/failing lines drawn in `drawBackground`, colours from the terminal theme via `SyntaxHighlighter`, 2-space tabs, auto-indent, smart quotes off); give it `.id(file)` so undo history is per file. Leaving a stack with unsaved edits asks first.
- System info and reboot: the Overview command has a labelled `##system` section (vendor, product, machine id, kernel, boot id, server time with offset and zone abbreviation) shown by `SystemInfoCard` (uptime and clock tick locally from the last poll). The same section carries `ip=` (the source address of the server's route to the internet, via `ip -4 route get 1.1.1.1`, which sends nothing) and `tailscale_ip=` (`timeout 3 tailscale ip -4`, falling back to the `tailscale0` interface); both are validated as dotted IPv4 (`OverviewParser.ipv4`) and optional in `Overview` so older cached snapshots decode. The card shows "IP address" always and "Tailscale IP" only when it is non-nil (nothing is mentioned for servers without Tailscale), each with a `CopyButton`. Reboot (`RebootSession` in Core; spec `reboot` and `boot_id`): a `.mutate` intent that checks `sudo -n` first (exit 5 `##no-sudo`, nothing scheduled), then schedules `systemctl reboot` two seconds out under `nohup` so the ssh command returns cleanly, and `waitForReturn` polls the kernel boot id every 4 s until it DIFFERS from the one read before (a successful connection alone proves nothing, the old system answers for a moment) or 10 minutes pass. `RebootFlow` (AppModel.swift) drives it and `RebootProgressBanner` shows waiting / back / timed out / failed; failing polls are not shown as errors while it is active. Reboot… is offered wherever the "reboot required" notice is: the Overview header, a button beside the attention chip (`AttentionAction`, `AttentionStrip(action:)`) and the Updates screen's reboot banner (`UpdatesScreen(reboot:rebootPending:)`: the confirmation is shown on the Updates screen itself, and `requestReboot(_, then:)` moves to the Overview once it is confirmed, because the sudo password sheet and the waiting/reconnect progress banner live only there). All three are disabled in Read-only mode and call `AppModel.requestReboot`. The notice itself is the SERVER's own flag: `/var/run/reboot-required` (created by Debian/Ubuntu's update-notifier-common apt hook when a kernel, libc, systemd etc. package was upgraded), read by the `overview` and `updates` scripts; Rackoon never decides a reboot is needed. A user whose sudo wants a password: `##no-sudo` puts the flow in `needsPassword` and the Overview shows `SudoPasswordSheet`; `RebootSession.reboot(sudoPassword:confirmation:)` runs the spec's `reboot_sudo` (`sudo -S -p ''` doing the whole nohup/systemctl as root in one sudo call) through the new `SSHTransport.run(_:input:timeout:)`, which writes the password plus newline to the command's stdin and nowhere else (not in the command text, so not in the confirm sheet, `ps` or logs; never on disk). It is a separate `Intent`/`confirmSudo()`, so a yes to the plain reboot never authorises it. `classifySudoFailure` (tested) turns sudo's text into `.badPassword` (the sheet asks again), `.sudoRefused` (requiretty, not in sudoers) or `.failed`. The protocol method has a default that throws `TransportError.inputNotSupported` (demo, fakes); `OpenSSHTransport` implements it with `input: .string`. Streamed root commands (apt actions on the Updates screen, `root` entries of the Commands library) use `SudoElevation` (Core): they run with `S='sudo -n'` first; if the output says sudo wants a password (`needsPassword`: classic "a password is required"/"a terminal is required", sudo-rs "interactive authentication is required"; text-based because a pipeline can exit 0, and it only ever OFFERS the sheet), the screen shows `SudoPasswordSheet` (`SudoRequest`, `.sudoPassword(_:)`, `.textContentType(.password)` so a password manager can fill it) and reruns the password variant: spec `sudo_prompt` put IN FRONT of the unchanged script, with a fresh 32-hex `{nonce}` per attempt (`SudoElevation.makeNonce`, `withPassword(_:nonce:)`, `AptAction.passwordIntent(nonce:)`, `CommandLibrarySession.passwordIntent(for:…nonce:)`; build the intent ONCE, the confirmation and the run must carry the same nonce). - A polled script's exit status is that of its LAST command, and `ServerSession`/`DockerSession` (Swift and Kotlin) treat non-zero as a failed poll and discard the output. The `overview` and `docker` scripts therefore end in `|| true`: both finish with a docker call, and on a server where docker is missing or the ssh user is not in the docker group that call exits 1 and made the whole Overview show "Command failed (exit 1)" (found on a real second server, 2026-10-13). The parsers judge the output instead: `##unhealthy` is simply empty, and `DockerParser` turns docker's error text into `.daemon`, whose description adds the `usermod -aG docker` advice when it says "permission denied". Any new polled script must end the same way or with a command that cannot fail.

## Paddle integration

When writing or modifying code that integrates with Paddle:

- Always check current Paddle documentation via the `paddle-docs` MCP server before suggesting code. The Paddle API and SDKs evolve frequently — do not rely on training data alone.
- Use the official Paddle SDK for the language in use:
  - Node.js → `@paddle/paddle-node-sdk`
  - Python → `paddle-python-sdk` (imports as `paddle_billing`)
  - Go → `github.com/PaddleHQ/paddle-go-sdk/v5`
  - PHP → `paddlehq/paddle-php-sdk`
- All development uses the sandbox environment. Sandbox API keys contain `_sdbx`; sandbox client-side tokens are prefixed with `test_`.
- Always verify webhook signatures before acting on the payload:
  - Node: `paddle.webhooks.unmarshal()`
  - Python: `Verifier().verify(request, secret)`
  - Go: `paddle.NewWebhookVerifier()` with `Middleware`
  - PHP: `(new Verifier())->verify($request, $secret)`
- For destructive account changes (updating prices, archiving products, canceling subscriptions), ask for explicit confirmation before calling the `paddle-sandbox` or `paddle-live` MCP server.
- Use `paddle-sandbox` by default. Only call `paddle-live` when the prompt explicitly mentions live, production, or real customer data.
- API keys and webhook secrets live in environment variables — never inline credentials into code.

Rackoon specifics: the Mac app is Swift and has no Paddle SDK, so it only opens a Paddle-hosted checkout link in the browser (Help > Feed the Rackoon…, `Supporter.swift`; the link is not a secret). There are no licence checks or feature limits. Today the link is the SANDBOX hosted checkout (product `pro_01m4k4708nn80m0gttd1cgh7z3`, one-time €100 price `pri_01m4k470p76n1yj2nk29rkpvpq`, tax added on top): before a release create the live product/price and hosted checkout (live hosted checkouts need Paddle approval) and replace both constants. Never put an API key in the app or the repo.
